# Data Stores

There is no relational application database. Three stores exist, each holding
one kind of thing:

| Store | Technology | Holds | Lifecycle |
|---|---|---|---|
| Vector index | Qdrant | Embedded PubMed abstracts | Rebuilt from `data/pubmed.jsonl` |
| Tracking store | SQLite (`mlflow.db`) | Training runs, params, metrics | Appended per sweep arm |
| Artefact store | Filesystem (`artifacts/`) | Weights, ONNX graphs, tokenizers | Regenerated by the pipeline |

None holds application state that cannot be rebuilt, which is why the serving
container is stateless apart from a read-only mount.

## Qdrant

### Collection

| Property | Value | Why |
|---|---|---|
| Name | `pubmed_abstracts` (`MEDEXTRACT_QDRANT_COLLECTION`) | |
| Vector size | Read from the encoder at build time | 768 for `pritamdeka/S-PubMedBert-MS-MARCO`. Never hardcoded — an encoder change must not silently produce a dimension mismatch. |
| Distance | `Cosine` | Vectors are L2-normalised at encode time, so returned scores are cosine similarities directly comparable across queries. |

Created by `retrieval/index.ensure_collection`, which is safe to call
repeatedly. `--recreate` drops first, which is required when the embedding
model changes: the old vectors would be in a different space and would rank
nonsensically against new queries.

### Point id

PMIDs are numeric strings, but Qdrant requires `uint64` or UUID and PMIDs are
not reliably either across the corpus. So:

```
point_id = uuid5(POINT_NAMESPACE, pmid)
POINT_NAMESPACE = 6f1c1f5e-6a3d-4c2a-9a56-0b6b1a1f9d21
```

Deterministic, so **re-indexing is idempotent** — a second pass updates
existing points rather than duplicating them. The PMID is also kept in the
payload, because a UUID is not something you can look a record up by.

Pinned by `test_retrieval.py::test_point_ids_are_stable_for_a_pmid` and
`::test_reindexing_is_idempotent`.

### Payload

| Key | Type | Notes |
|---|---|---|
| `pmid` | string | The natural key; the id is derived from it, not the reverse |
| `title` | string | |
| `abstract` | string | Sections joined with their labels |
| `journal` | string \| null | |
| `year` | integer \| null | |

Returned to the caller directly by `Searcher.search`; see
[SPEC.md](SPEC.md#post-search).

**No payload indexes.** At a few thousand points there is nothing to filter on
and no query that would use one. Adding date or journal filters would need
them.

### What is embedded

`Abstract.text` — title, blank line, abstract body. Title and abstract share a
vector rather than being separate points. At this corpus size the simpler
model retrieves well enough; splitting them would double the point count and
require a merge step at query time for no demonstrated gain.

Truncation is at 256 tokens (`OnnxEmbedder.max_length`), so long abstracts are
represented by their opening — which is where the topic sentence is.

### Writes

Batched upserts of 128 points (`index.UPSERT_BATCH`). Progress is logged per
batch, so a long index build shows movement rather than appearing hung.

**No hashing-vector fallback when building.** `build_embedder` is called with
`allow_fallback=False`. The service *does* fall back to hash embeddings if the
real encoder cannot load, so it keeps answering — but an index built from hash
vectors looks fine, retrieves badly, and costs a full pass over the corpus to
rebuild. Failing loudly is cheaper. `--allow-hashing-fallback` overrides it for
smoke tests.

### Deployment modes

`retrieval/index.build_client` accepts three forms:

| `MEDEXTRACT_QDRANT_URL` | Mode | Use |
|---|---|---|
| `http://...` | Server | Docker compose, production |
| `:memory:` | Embedded, in-process | Tests |
| Any filesystem path | Embedded, on-disk | No Docker daemon available |

The on-disk mode is what lets the whole system run from a checkout with no
daemon. `pipeline.py` selects it automatically when `docker info` fails.

### Capacity

At 3,000 abstracts × 768 float32 dimensions the raw vectors are about 9 MB;
payloads dominate at roughly 2–3 KB per abstract, so on the order of 10 MB
total. Qdrant's default HNSW settings are untouched — at this scale the index
build is seconds and recall is effectively exact.

This is a demonstration corpus. Recall against the full ~35M-record PubMed is
not a claim being made; see [PRD.md](PRD.md).

### Durability

Docker compose mounts a named volume `qdrant_storage` at `/qdrant/storage`, so
the index survives `docker compose down`. It is still derived data — losing it
costs one `make fetch && make index`.

**No backup procedure, deliberately.** Backing up a derived index that rebuilds
in minutes from a JSONL file that is itself re-fetchable would be ceremony.

## MLflow tracking store

SQLite at `mlflow.db`, addressed as `sqlite:///<repo>/mlflow.db` by
`config.mlflow_tracking_uri()`.

**Why not the `./mlruns` file store.** Two reasons: MLflow 3 put that backend
into maintenance mode and now raises rather than opening one, and it writes a
tree of thousands of very small files — one per metric and per parameter per
run. Nine arms of that inside a synced folder is a lot of churn for data a
single file holds just as well.

Schema is MLflow's own (`experiments`, `runs`, `params`, `metrics`, `tags`);
nothing here extends it. What gets written is listed in
[DATA_MODEL.md](DATA_MODEL.md#tracking-store).

Read by `report.py` via `mlflow.search_runs` to generate
[sweep_table.md](sweep_table.md). Keeping the table generated is the point —
it cannot drift from the runs that produced it.

To inspect it directly:

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

## Filesystem artefacts

Layout is in [DATA_MODEL.md](DATA_MODEL.md#on-disk-layout).

Two policies keep it from growing without bound:

- **Checkpoints are pruned.** The Trainer's per-epoch checkpoints are consumed
  by `load_best_model_at_end` and then deleted; only the final `model/`
  survives. Nine arms would otherwise leave several gigabytes of optimiser
  state behind.
- **Weights are not logged to MLflow.** `log_model_artifact` defaults to false,
  so the tracking store gets `config.json`, the tokenizer files and a
  `model_dir` tag rather than a second copy of every arm.

Everything under `artifacts/`, `data/`, `mlflow.db` and `mlartifacts/` is
gitignored. It is all reproducible and none of it belongs in version control.
