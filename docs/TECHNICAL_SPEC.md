# Technical Specification

Implementation-level detail: the algorithms that are easy to get subtly wrong,
and how each is pinned. Component overview is in
[ARCHITECTURE.md](ARCHITECTURE.md); data shapes in
[DATA_MODEL.md](DATA_MODEL.md).

## 1. Label alignment (`labels.py`)

**The problem.** Annotations are per *word*. The model sees WordPiece
*subwords*, and biomedical vocabulary fragments hard — `Adenomatous` becomes
`Aden ##oma ##to ##us`. Labels must be projected onto the subword sequence.

**The mechanism.** `word_ids()` from the fast tokenizer gives, for each subword
position, the index of the word it came from, or `None` for special tokens.

```
words     : ["the", "adenomatous", "polyposis"]
labels    : [ "O",  "B-Disease",   "I-Disease"]
subwords  : [CLS] the aden ##oma ##tous poly ##posis [SEP]
word_ids  : None   0    1     1      1     2      2   None
aligned   : -100   O  B-Dis -100  -100  I-Dis  -100  -100
```

Special tokens always get `IGNORE_INDEX` (`-100`), which
`CrossEntropyLoss` skips. Continuation subwords have two defensible
conventions:

| `label_all_subwords` | Continuations get | Notes |
|---|---|---|
| `False` (default) | `-100` | The standard HuggingFace recipe and what the published baselines use. The reported F1 is produced this way. |
| `True` | `B-X` → `I-X`, others unchanged | Implemented and run as a sweep arm rather than argued about. |

**Why it is isolated.** Getting this wrong does not throw. The loss still
falls, training still looks healthy, and the F1 is quietly wrong. `labels.py`
therefore has no heavy imports so it can be unit-tested without touching
`datasets`, and `test_labels.py` asserts exact label *positions* against a real
fast tokenizer — not merely that the lengths agree.

## 2. Tokenizer casing (`tokenization.py`)

**The problem.** A checkpoint with no `tokenizer_config.json` gives
`AutoTokenizer` nothing to read casing from, so it falls back to the BERT class
default of `do_lower_case=True`. Against a *cased* vocabulary that is
destructive:

| Term | Default (wrong) | With `do_lower_case=False` |
|---|---|---|
| `APC` | `a ##p ##c` | `AP ##C` |
| `EGFR` | `e ##g ##f ##r` | `E ##G ##F ##R` |
| `Adenomatous` | `ad ##eno ##mat ##ous` | `Aden ##oma ##to ##us` |

The cased vocabulary has no lowercase entry for a gene symbol, so each one
shatters into single characters. `dmis-lab/biobert-base-cased-v1.2` is exactly
this case: its repository contains only `config.json`, `pytorch_model.bin` and
`vocab.txt`.

**The mechanism.** Decide from the *vocabulary*, not from the model name:

```
content tokens := vocab minus special tokens and [bracketed] placeholders
cased          := (uppercase-containing content tokens / content tokens) > 1%
```

`bert-base-uncased` carries uppercase only in its five special tokens; exclude
those and the ratio is zero. `bert-base-cased` is above 20%. There is no
checkpoint in between. Excluding specials also matters because on a small
vocabulary they alone would cross the threshold.

If the vocabulary is cased and the tokenizer is lowercasing, it is reloaded
with `do_lower_case=False`. Then a probe string is tokenised and the result
checked — if case still did not survive, it raises rather than warns. A run
that trains on shredded input costs far more to discover later.

The corrected setting is written into the saved `tokenizer_config.json`, so the
ONNX export and the serving container inherit it.

## 3. Corpus loading (`data.py`)

**The problem.** `load_dataset("ncbi_disease")` fails on any current install.
The Hub repository contains a loader *script* and no data files, and `datasets`
3.0 removed script execution.

**The mechanism.** Three sources, tried in order of how little they assume:

| # | Source | Notes |
|---|---|---|
| 1 | `load_dataset(hf_id, revision="refs/convert/parquet")` | The Hub's automatic conversion. Generated by the Hub, not published by the owner, so convenient but not depended on. |
| 2 | `load_dataset(hf_id)` | In case the repository gains real data files. |
| 3 | Direct download of the upstream corpus files | The same files the official loader script fetches. |

Each failure is logged and the next tried; exhausting all three raises an error
naming every attempt. The source that answered goes into the MLflow record.

**Source 3 formats.** Two parsers, one output shape:

- `conll` — two-column TSV, `token<TAB>tag`, blank line between sentences.
  Splitting on tab and taking the first two fields is exactly what the official
  script does.
- `jsonl` — `{"tokens": [...], "tags": [...]}` per line with integer tags
  indexing the configured label names.

Both build a `DatasetDict` with a real `ClassLabel` feature, so
`resolve_label_names` recovers the vocabulary from the dataset and nothing
downstream can tell the sources apart.

**One deliberate difference.** The official script emits an empty example at
end-of-file when the file ends with a blank line; the parser here drops it.
Split sizes therefore differ by one per split (5432/923/940 direct versus
5433/924/941 from the parquet conversion). An example with no tokens has no
gold spans and no predicted spans, so it cannot move entity-level F1 either
way.

## 4. Entity-level scoring (`metrics.py`)

**Why not token accuracy.** Most tokens are `O`. A model predicting nothing
scores above 90%. `test_metrics.py::test_predicting_nothing_scores_zero_not_high`
asserts exactly that failure mode.

**Strict IOB2 span extraction.** Only `B-X` opens a span. `I-X` extends an
already-open span of type `X`; an `I-X` anywhere else is an invalid transition
and is *discarded*, not repaired. This matches seqeval's
`mode="strict", scheme=IOB2`, which is how published NCBI-Disease numbers are
produced.

Micro-averaged precision/recall/F1 over exact `(type, start, end)` matches,
plus per-type figures, returned as flat scalars because MLflow metrics are
scalars.

**Why hand-rolled.** seqeval 1.2.2 ships only an sdist whose `setup.py` no
longer builds against current setuptools; it fails at metadata generation,
which would break both CI and the Docker build. The logic is about sixty lines,
and `test_metrics.py::test_matches_seqeval_on_random_sequences` cross-checks it
against seqeval across 25 randomised trials whenever seqeval happens to be
importable. So it is verified rather than merely asserted.

## 5. Span decoding (`inference.py`)

**Subwords are collapsed to words first.** Only a word's first subword was
supervised during training (see section 1), so a continuation's prediction is
untrained noise. Reading it splits entities apart: `nephrotoxicity` predicted
`B-Disease, O, I-Disease, O, O, O` across its six pieces decodes per-subword to
the fragments `"ne"` and `"rot"`. `_collapse_to_words` takes each word's label
and score from its first subword and its span from first start to last end.

Evaluation never saw this, because `metrics.decode_predictions` drops exactly
the positions that cause it. The two paths now agree on granularity, which is
what makes the reported F1 predictive of served output at all. See
[ADR-017](DECISIONS.md#adr-017).

Then the BIO state machine runs over words:

```
for each position:
    skip if special token or padding      (both carry offset (0,0))
    skip if token_end <= token_start      (zero-width pieces)
    if label is O:                        flush current span
    elif prefix is B or type changed:     flush, open new span
    else:                                 extend span, accumulate score
flush
```

Score is the mean confidence over the span's tokens.

**Deliberately more lenient than scoring.** An orphan `I-X` opens a span here.
Models do emit that, and refusing to return an entity because the prefix was
malformed helps no caller. Evaluation discards it because the baselines do.
Both behaviours are pinned by tests so neither drifts into the other; see
[DECISIONS.md](DECISIONS.md#adr-004).

## 6. Windowing (`inference.py`)

Inputs longer than `max_sequence_length` are tokenised with
`return_overflowing_tokens=True` and `stride=32`, producing overlapping
windows. `overflow_to_sample_mapping` maps each window back to its source text.
Windows are decoded independently, then merged:

```
key = (start, end, label)
keep the highest score for any key seen more than once
sort by (start, end)
```

So an entity at character 8,000 is found, and one that falls inside the overlap
is not returned twice.

## 7. ONNX export and parity (`export_onnx.py`)

**Export.** `torch.onnx.export` with everything pinned explicitly — input
names, output names, dynamic axes, opset 14 — rather than inherited from a
converter's defaults. Batch and sequence are both dynamic, so one graph serves
single requests and batches. The model is wrapped in a `LogitsOnly` module so
the graph has one clean output tensor instead of a `ModelOutput`.

`dynamo=False`: torch 2.6's dynamo exporter pulls in onnxscript and mishandles
external data for small graphs.

Tokenizer and config are copied alongside the graph. The serving image loads
everything from that one directory and never sees the PyTorch checkpoint, so
anything the runtime needs has to be there.

**Parity, in increasing order of what a caller cares about:**

1. Max absolute logit difference within `atol=1e-4`, `rtol=1e-3`.
2. Argmax agreement — the predicted label per token.
3. Identical decoded entity spans across both backends.

Both backends are fed the *same* tokenised batch, so any difference is the
graph. The check runs before any timing and hard-fails on mismatch: a benchmark
of a graph that quietly computes something different is a benchmark of the
wrong thing.

Bit equality is not on offer — ONNX Runtime and PyTorch fuse and schedule
kernels differently. 1e-4 on logits is tight enough that neither argmax nor the
softmax confidences move.

## 8. Benchmarking (`benchmark.py`)

Tokenisation is done once and hoisted out of the timing loop: it is identical
across backends, so including it would dilute the difference being measured.
End-to-end request latency is what `/extract`'s own logging reports.

Percentiles rather than means — the mean hides the tail and the tail is what a
caller notices. Warmup iterations are discarded. Hardware, thread settings and
library versions are recorded into `docs/benchmark.json`, because a speedup
number without them is not a claim anyone can check.

## 9. Batch resolution (`train.py`)

`batch_size` is the *effective* batch size — what the optimiser steps on, and
what the comparison table means by "batch".

```
per_device    = min(batch_size, max_per_device_batch)
accumulation  = round(batch_size / per_device)
```

The product always equals `batch_size`, so an arm means the same thing on a
4 GB laptop card as on a datacentre GPU. Both numbers go into the MLflow
record. If an arm still runs out of memory, `sweep.run_sweep` retries it once at
half the per-device batch — an OOM becomes a slower arm, not a lost one.

## 10. Query encoder export (`retrieval/export_embedder.py`)

The container runs onnxruntime and carries no PyTorch, so the query encoder has
to be an ONNX graph too — not just the NER model. `sentence-transformers` would
drag torch back in.

The graph emits `last_hidden_state`; pooling and L2 normalisation happen in
numpy at query time. That keeps the export a plain transformer forward pass and
lets the pooling mode be read from config at load rather than baked into the
graph.

Pooling is read from the model's own `1_Pooling/config.json` rather than
assumed, because getting it wrong produces embeddings that are subtly wrong
rather than obviously broken: search still returns results, they are just
worse.

Mean pooling masks out padding. Averaging padding drags every vector toward the
pad embedding and shortens short texts' effective norm.

## 11. Request context (`api/logging_config.py`)

The request id lives in a `ContextVar` set by the middleware, and the JSON log
formatter reads it. That is why log lines emitted by library code — which knows
nothing about the web layer — still carry the id, without threading a parameter
through every call site.

## 12. Environment guards (`__init__.py`)

Two import-time defences, in the one module every entry point goes through:

- **Arrow before torch.** Importing pyarrow after torch and transformers have
  initialised kills the process on Windows with an access violation — a
  segfault, not an exception. Both ship overlapping native dependencies and only
  load order decides whether they coexist. No-op where pyarrow is absent, which
  is the serving container.
- **`USE_TF=0`.** `transformers.Trainer` imports its reporting integrations,
  which reach for `TFPreTrainedModel`, which raises outright when the installed
  TensorFlow is paired with Keras 3. Nothing here touches TensorFlow, so a TF
  install that happens to be on the machine should have no say in whether
  training starts. `setdefault`, so it remains overridable.

## 13. Tokenizer capability (`tokenization.py`)

Two things downstream need from the tokenizer: `word_ids()` for label
alignment and an offset mapping for character spans. Both existed only on the
Rust-backed tokenizers while transformers also shipped pure-Python ones, and
the guard used to read `is_fast` as a proxy. From 5.x every tokenizer is
Rust-backed and reports `is_fast=True`, so a guard on the flag either never
fires or has to be pinned to a library version — which is what the old
`transformers<5` pin was.

`supports_word_alignment` asks the question directly: tokenise a two-word
probe with `is_split_into_words=True` and `return_offsets_mapping=True`, then
call `word_ids()`. A tokenizer that cannot do either raises
(`NotImplementedError`, `ValueError`) and the guard raises its own error naming
what is missing. The same code gives the same answer on 4.x and 5.x, which is
what lets the suite run on both.

Pinned by `test_data.py::test_the_guard_is_decided_by_capability_not_by_the_is_fast_flag`,
which feeds it an object whose flag says fast and whose behaviour says
otherwise.

## 14. Artefact integrity (`integrity.py`)

`check_parity` hashes `model.onnx` after the comparison passes and writes the
digest into `parity.json`. `NerEngine._init_onnx` hashes the file it is about
to open and compares, before `onnxruntime` ever sees it:

| Record | File | Result |
|---|---|---|
| present, matches | — | load, `integrity_verified=True` |
| present, differs | — | `IntegrityError`, both hashes in the message; `/health` degraded, `/extract` 503 |
| absent | — | load, `integrity_verified=False`, warning logged |

An absent record is a weaker claim, not a contradiction, which is why it
degrades the report rather than refusing the load. The hash is streamed in
1 MB chunks: a 436 MB graph is hashed in about a second at startup and never
held in memory whole.

The torch backend serves weights no export record describes, so it reports
`model_sha256: null` and `integrity_verified: false` rather than inventing a
check it cannot make.

## 15. Prepared attention mask for export on transformers 5 (`export_onnx.py`)

transformers 5 builds BERT's attention mask through utilities that read the
shape of a position tensor; under the TorchScript tracer that tensor is a
scalar and the export dies with `IndexError` inside `sdpa_mask`. The same
utilities return a mask untouched when it already has the prepared 4-D shape
`(batch, 1, query, key)`.

So on 5.x the export wrapper builds that mask itself from the 2-D padding
mask — zero where a token may be attended to, the float minimum where it may
not, the additive form BERT has always used internally — and passes it
through. On 4.x the wrapper passes the 2-D mask as before. The decision is
made once per export from the library's major version.

The graph that comes out is the same graph: on the shipped checkpoint, logits
from the 5.x export match the 4.x export to 4.6e-6 on every real token, and
both match the PyTorch forward on either version to within the parity
tolerance.

## 16. Type restriction (`data.py`)

`restrict_types(raw, spec, label_names, keep_types)` turns a multi-type corpus
into a single-type one: every mention of a type not in `keep_types` becomes
`O`, and the label list shrinks to `O` plus the kept types' tags. It exists so
that "does a combined Disease + Chemical model match two specialised ones?"
can be answered on exactly the same sentences — the two arms differ in nothing
but the labels.

The relabelled tags are returned as strings with the column's feature type
declared as `Sequence(Value("string"))`. Without that declaration `datasets.map`
re-encodes the strings through the column's existing `ClassLabel`, into the
original integer space, silently ([BUGS.md B13](BUGS.md#b13--datasetsmap-re-encoded-restricted-tags-into-the-wrong-label-space)).
